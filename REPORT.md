## 1. What ORIGIN does

A deterministic engine finds the root cause. A model is called only to break a
tie, and it is never allowed to write the answer.

```
0 parse case      instruction -> window (UTC+8), failure count, fields asked
1 load window     only the window + a 60-min baseline; metrics, trace edges, error logs
2 anomalies       robust z vs baseline median/IQR, sustained over k samples -> onsets
3 candidates      group signals by component, rank, CAUSAL FILTER, legal reasons
4 route           gate (no model) -> GLM-4.7-Flash -> GLM-5.2 on escalation
5 validate        candidate id + legal reason -> answer; code writes every number
6 render          prediction (exact key order) + grounded evidence markdown
```

Stages 0–3 and 5–6 are plain Python. Models appear only in stage 4, and their
output vocabulary is a candidate ID (`C3`) and a reason from a fixed list.

**The causal filter (stage 3) is the idea the whole design rests on.** When one
component fails, everything downstream of it also looks broken — usually louder
than the cause. So a candidate is demoted when something it *calls* went wrong
*earlier*: if A calls B and B's anomaly started first, A is a symptom. The call
graph comes from parent/child spans in `trace_span.csv`; containment (pod→node)
and grouping (pod→service) come from `cmdb_id` naming.

**Why the model cannot fabricate.** It returns `{"candidate": "C3", "reason":
"container read I/O load"}`. A candidate ID that does not exist, or a reason
illegal for that candidate's level, causes the whole reply to be discarded — not
partly used. The component name comes from the candidate, and the timestamp from
the onset of the signal that votes for the *chosen* reason, so the answer and the
evidence behind it cannot disagree.

## 2. How we evaluate

**Splits.** The 70 dev cases were split by `eval/split.py` into **49 dev_tune**
and **21 holdout** (stratified, 3 per task type), by `row_id`, committed in
`eval/splits/split.json` **before any tuning**. All parameter changes were made
against dev_tune only. Holdout per-case results were not opened until CP4.

**Configurations.**

| config | what it is |
|---|---|
| `heuristic` | the starter baseline, no model — the floor |
| `engine` | our engine, no model at all |
| `single-flash` | one GLM-4.7-Flash call per case, no gate, no escalation |
| `single-strong` | one GLM-5.2 call per case, no gate, no escalation |
| `routed` | gate → Flash → GLM-5.2 on escalation |
| `routed-flash` | gate → Flash, never escalate (added after the breakdown below) |

`routed` and `single-strong` are the comparison `docs/scoring.md` asks for.

**Repeats.** Model configs are run more than once because they are
non-deterministic; means over repeats carry a standard deviation, and any `n=1`
row is labelled.

**Two honesty notes about the numbers.**

1. **Seconds in the eval tables are contended.** Several configs were run as
   concurrent processes on one laptop to fit the schedule, which inflates
   wall-clock per case. **The authoritative timing is the Docker measurement in
   §6**, taken at the judged configuration (2 CPU, 8 GB) with nothing else
   running. Dollars and scores are unaffected by contention.
2. **The engine cache makes repeat runs look faster than they are.** Repeats reuse
   a per-day metric cache the judged run will not have, so their engine time is
   near zero. We built a hook to bill the cold seconds instead, but nothing
   populates it, so **it is not active** -- rather than imply otherwise, we quote
   **repeat 1 only** (cold, honest) and the Docker measurement in section 6 for
   any timing claim. Accuracy and dollars are unaffected by caching.

## 4b. A measurement error we made, and how the eval caught it

> ⚠️ **STALE NUMBERS — re-measure before submitting.** Everything in this section
> was measured against the engine as it stood before Person 1's Phase-4 tuning
> (dev_tune 0.539 → 0.5747). The *methodological* point stands unchanged; the
> figures must be re-derived from the current `eval/results/per_case.csv`.

Breaking `routed` down by the route each case took made it look as if only the
strong tier was harmful:

| route | n | engine would score | routed scored |
|---|---|---|---|
| `gate` (no model) | 11 | 0.727 | 0.727 |
| `flash` decided | 6 | 0.667 | **0.667** |
| escalated to GLM-5.2 | 30 | 0.447 | **0.325** |

We read that as "Flash is harmless, the strong tier is the problem", and built
`routed-flash` (gate → Flash, never escalate) expecting it to recover most of the
engine's accuracy.

**It did not: 0.476 against the engine's 0.539.** The breakdown was conditioned on
the outcome. A case only *stays* on the `flash` route when Flash **agrees** with
the engine — disagreement is itself an escalation trigger — so the six `flash`
cases were a sample selected for having no effect. Every case where Flash would
have changed the answer had already been promoted to `strong` and left the sample.

The plain reading is the correct one: **consulting a model on an ambiguous case
costs accuracy, whichever model it is.** We keep this here because inspecting the
breakdown would have shipped the wrong conclusion, and running the experiment is
what caught it.

## 5. Where it fails

**Blind spot we can name precisely: `container process termination`.** It is
invisible in this bundle's telemetry — no series stops, no restart signature, no
error log lines, in either dev_tune case that has it (see `docs/data-notes.md`).
3 of 55 dev reasons are process termination, and we expect to score zero on them.

**Reason-only tasks (task_2, task_4) are the weakest.** They turn on separating
reasons *within* the network group (latency vs packet loss vs retransmission vs
corruption), which several KPIs vote for simultaneously.

The per-scoring-point taxonomy — whether the time, the component or the reason
was the thing that missed — is table §6 of the generated summary.

## 8. Honest caveats

- **n = 21 on the holdout.** `docs/scoring.md` treats one or two cases as a tie,
  and so should any reading of our table. The standard deviations across repeats
  are the honest measure of what a difference has to beat.
- **dev_tune numbers are optimistic by construction** — parameters were chosen
  against them. Only the holdout table is a fair estimate, and even that is
  from the same deployment; the judged 20 cases come from a different one.
- **Seconds in the eval tables are contended** (see §2); trust §6.
- **We changed one starter file.** `llm.py` now reads `message.reasoning` when
  `content` is blank, because Featherless returns the answer there on both Flash
  models — the unpatched client returns `""` on every GLM-4.7-Flash call while
  still being billed. Token accounting is untouched. See `ATTRIBUTION.md`.
- **Our confidence signal did not come out calibrated.** See the calibration
  table in the generated summary; we report it as a result rather than dropping it.
